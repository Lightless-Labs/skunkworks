1. **R1–R2, R12:** Deliver one Rust source file in `rust` fences, compatible with `rustc --edition 2024`, using only `std`, without inner attributes/docs. Preserve exact API names, types, variants, and derives; all specified items and fields are public. `Range` has implementation-chosen representation.

2. **R3, R20:** Versions require exactly three core numbers; accept no trimming, prefix, signs, Unicode, or surrounding whitespace. Only `""` yields `VersionError::Empty`. Preserve suffix spelling, case, and identifier order; absent suffixes produce empty vectors.

3. **R4, R6:** Process core fields left to right, consuming maximal ASCII digit runs. No digits means `MissingCore` at the field start for EOF, `.`, `-`, or `+`; any other byte means `InvalidChar`. After major/minor, require `.`: EOF/`-`/`+` means `MissingCore`, anything else means `InvalidChar`. After patch, only EOF/`-`/`+` is allowed.

4. **R5, R9:** Validate each consumed core number before its following separator: multidigit leading zero wins over overflow, and both win over separator errors. Zero and `u64::MAX` are valid; larger values overflow. Report numeric errors at the field start; prevent arithmetic wraparound.

5. **R7–R9:** Both suffix kinds require nonempty, dot-separated identifiers containing only ASCII letters, digits, or hyphen. Hyphen is ordinary content, even alone. The first `+` ends pre; build continues to EOF, so another `+` inside build is invalid. Numeric build identifiers may have leading zeros.

6. **R7–R8, R19:** Fully validate an identifier’s characters before checking its numeric leading zero: `1.2.3-01!` reports `InvalidChar`. Process identifiers sequentially, completing pre before build; an earlier identifier’s leading-zero error wins over later invalid characters. Empty identifiers report their start, including EOF or a `+` ending pre: `1.2.3-+x` reports `EmptyIdentifier { at: 6 }`.

7. **R8–R9, R11:** Only all-digit pre identifiers are numeric. They have unlimited length and never overflow; multidigit ones starting with zero are invalid. Compare valid numeric identifiers by length, then ASCII bytes—not integer conversion. Identifiers such as `01a` are nonnumeric and valid.

8. **R2, R10–R11:** Compare core tuples numerically, then pre; a release outranks every prerelease of the same tuple. Numeric pre identifiers precede nonnumeric ones; nonnumeric comparison is case-sensitive ASCII lexicographic order. Equal common prefixes favor the shorter list. Comparison ignores build, but derived `Version` equality retains it.

9. **R3, R12–R13:** Every offset is a zero-based UTF-8 byte offset. Range errors use the original range string; nested `VersionError` offsets remain operand-relative. Only ASCII space/tab/CR/LF separate tokens; leading/trailing runs are accepted. Empty or whitespace-only ranges return `RangeError::Empty { at: 0 }`; Unicode whitespace is not a separator.

10. **R14–R15, R21:** Select the longest supported comparator prefix, then require an immediately attached, nonempty operand beginning with an ASCII digit. Failure yields `Syntax` at token start; otherwise wrap `parse_version` failures at operand start. Thus `==1.2.3` is syntax, while `1.2` and `1.2.3,` yield wrapped version errors. Reject unsupported range grammar.

11. **R14, R16, R21:** The entire accepted range is one conjunction; there is no OR grammar. Parse tokens left to right and return the first error, even after already contradictory comparisons. Contradictions parse successfully and match nothing; duplicates have no effect. Bare versions mean equality, and all comparison boundaries ignore build metadata.

12. **R17–R18:** A prerelease candidate must both satisfy every comparator and have its exact core tuple represented by an explicit prerelease operand in that conjunction. Admission alone does not establish a match. Other tuples and build-only operands cannot grant admission; stable candidates need no admission.
