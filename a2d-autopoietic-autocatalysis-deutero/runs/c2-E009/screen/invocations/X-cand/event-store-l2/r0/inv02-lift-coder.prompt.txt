R4. Process events in slice order. Each successful event increments version by exactly one, including Open and Close. Compare event fields to the pre-event state. There are no implicit events, fees, resets, or reopening.

R5. replay returns the final account on success, or the first failing event as ReplayError with its zero-based slice index. Later events are not examined. No partial account is returned.

R6. Events are not deduplicated during replay: identical repeated valid events each apply and count toward version. Returning to balance zero does not reset version. R7. Open first checks limit: it must be in 1..=1_000_000_000, otherwise InvalidLimit, even on an already opened or closed account.

R8. After the limit check, Open requires status New; either Open or Closed instead yields AlreadyOpened. Success sets status Open and limit to the given value, leaving balance zero.

R9. Deposit checks lifecycle before amount: New yields NotOpened, Closed yields Closed. Only Open proceeds to field checks.

R10. Deposit amount must be strictly positive, otherwise InvalidAmount. This check precedes checking available capacity.

R11. Deposit then requires amount <= limit - balance, otherwise LimitExceeded. Equality succeeds. Test without overflowing i64, including amount i64::MAX; success adds amount to balance.

R12. Withdraw checks lifecycle exactly as Deposit, then requires amount > 0 or yields InvalidAmount. These checks precede all floor and balance checks.

R13. Withdraw next requires floor in 0..=limit, otherwise InvalidFloor. Floor validity is checked even when funds are insufficient.

R14. Withdraw next requires amount <= balance, otherwise InsufficientFunds. This precedes FloorViolation and must handle i64::MAX safely.

R15. Withdraw finally requires balance - amount >= floor, otherwise FloorViolation. Equality succeeds. Success subtracts amount; floor is an event-local constraint and is never stored.

R16. Close first checks lifecycle exactly as Deposit. Closing New is NotOpened; closing Closed is Closed, regardless of expected_version.

R17. Close next compares expected_version with current version. Mismatch yields CloseVersion { expected: the event value, actual: current version }, even when balance is nonzero.

R18. After a matching close version, nonzero balance yields NonZeroBalance. Zero balance closes successfully.

R19. Closed accounts retain limit and zero balance, and remain Closed forever. Events never implicitly create accounts except Open; depositing/withdrawing after close fails as specified above.
