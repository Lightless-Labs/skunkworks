## requirements

Implement in Rust as a SINGLE source file that compiles with rustc --edition 2024, std only. Output ONLY the Rust source code inside ```rust fences.

Public API (all listed items and fields must be pub; enums and structs derive Debug, Clone, PartialEq, Eq):
```rust
pub struct PatchOptions { pub max_offset: usize, pub fuzz: usize }
pub enum ApplyError {
    InvalidOptions,
    BadHeader { line: usize },
    BadHunkHeader { line: usize },
    BadBody { line: usize },
    CountMismatch { line: usize },
    Misordered { line: usize },
    SourceFormat { byte: usize },
    SourceMissingLf,
    TooLarge,
    NoMatch { hunk: usize },
    Ambiguous { hunk: usize, first: usize, second: usize },
}
pub fn apply_unified(source: &str, patch: &str, options: PatchOptions) -> Result<String, ApplyError>;
```

R1. Implement exactly the public API above; PatchOptions fields control application, not parsing.
R2. Options must satisfy max_offset<=16 and fuzz<=2. InvalidOptions precedes all other errors.
R3. All patch error line numbers are one-based physical line numbers; hunk numbers are one-based. Candidate positions in Ambiguous are zero-based full hunk starts in the current working source.
R4. Empty patch contains no hunks and is an identity patch; still validate source and options.
R5. Nonempty patch must end with LF. Check this before other patch syntax; if absent return BadHeader at 1 plus the number of LFs in patch.
R6. A nonempty patch starts with exactly "--- before" and "+++ after" on lines 1 and 2. Return BadHeader at the first missing or unequal header line.
R7. After the two file headers there must be at least one hunk; otherwise BadHunkHeader{line:3}.
R8. A hunk header must be exactly "@@ -A,B +C,D @@" with single spaces and all four numeric fields explicitly present.
R9. Each numeric field is canonical ASCII unsigned decimal, with no sign or leading zeros except the single digit 0, and has value at most 128. Any failure is BadHunkHeader at its header line.
R10. A and C are one-based when their respective counts B and D are positive, and zero-based anchors when the count is zero. Positive count with zero start is BadHunkHeader.
R11. The old nominal zero-based full start is A-1 for B>0 and A for B=0; the new full start is C-1 for D>0 and C for D=0.
R12. A body runs until the next physical line beginning with "@@", or patch end. Such an "@@" line begins a new header even if malformed.
R13. Each body row has exactly one prefix space, minus, or plus followed by an arbitrary UTF-8 payload without CR. Empty payloads are valid; unprefixed empty rows and any other prefix are BadBody at that row.
R14. Body old count is the number of space and minus rows; new count is the number of space and plus rows. After validating all rows of that body, mismatch with B or D is CountMismatch at its header.
R15. After count validation, require at least one plus or minus row; otherwise BadBody at the header line, including a 0,0 empty hunk.
R16. After these checks, hunks must be ordered and nonoverlapping in nominal old coordinates: each full start must be at least the previous old start plus its old count. Same-anchor zero-length hunks are allowed.
R17. Also require each nominal new full start to equal its nominal old full start plus the sum of (D-B) over preceding hunks, using signed arithmetic. A negative required new start is invalid. Either ordering violation is Misordered at the current header.
R18. Allow at most 16 hunks, inclusive. A structurally valid seventeenth hunk returns TooLarge after its ordering checks; do not inspect later hunks.
R19. Parse hunks in order, with each hunk checked in the order just specified. Complete patch parsing before validating source or trying any match. A later parse error therefore precedes an earlier application failure.
R20. Source is UTF-8 text: empty means zero lines; otherwise it must end in LF. Splitting removes terminators and a final LF adds no extra line; blank lines count.
R21. Validate source in this order: first CR byte gives SourceFormat with its zero-based UTF-8 byte offset; then absent final LF gives SourceMissingLf; then more than 128 source lines gives TooLarge.
R22. Match payloads exactly, without normalization. Work on a private copy and apply hunks sequentially; failure returns only the error and no partially applied text.
R23. For fuzz, let lead and trail be the counts of contiguous space-prefixed rows at the beginning and end of this hunk body. Choose dropped counts L<=min(fuzz,lead) and R<=min(fuzz,trail). Never drop a plus or minus row.
R24. Dropping means ignoring those L leading and R trailing context payloads for matching and preserving the corresponding actual source lines unchanged. A dropped context line must still exist.
R25. A candidate full start s is any position with 0<=s and s+B<=current_source_line_count, even with fuzz. For B=0, insertion at end is allowed.
R26. The expected full start for a hunk is nominal_old_start + net + drift. net starts at 0 and is the sum of D-B for already applied hunks. drift starts at 0 and retains relocation across hunks.
R27. A candidate is allowed when the absolute signed distance from s to expected is at most max_offset. Expected may be negative or beyond source end; do not clamp it.
R28. For a choice (s,L,R), collect space and minus payloads from the body after removing those edge rows; they must equal current_source[s+L .. s+B-R] in order.
R29. Rank matching choices first by L+R, then by absolute offset distance. Thus an exact-context match anywhere in range outranks a closer fuzzed match.
R30. If no choice matches, return NoMatch with this hunk number.
R31. Among choices with the best rank, if two or more distinct full starts remain, return Ambiguous with the two numerically smallest starts; do not break a positional tie by earlier occurrence.
R32. If several best choices have the same full start, choose the smallest L (and hence the corresponding R); this tie is not Ambiguous.
R33. Replace only current_source[s+L .. s+B-R] with the space and plus payloads of the trimmed body in their body order. Prefixes themselves never enter output.
R34. After replacement, more than 128 working lines returns TooLarge before proceeding to the next hunk.
R35. After successful application update net by D-B and set drift to s-(nominal_old_start + previous_net); the accepted displacement is carried into the next hunk.
R36. Actual relocated hunks may revisit earlier working lines; only nominal ordering is enforced.
R37. On success serialize all working lines with exactly one LF after every line, including the last; zero lines serialize as an empty string.
R38. The input patch and source remain unchanged. File headers are metadata and never source or output lines.
